# ADR-0050: Publish npm packages only from published GitHub Releases

## Status

Accepted

## Context

Temple's first npm publication required an interactive browser login and second-factor ceremony. Repeating that sequence for every version is cumbersome, while publishing on every merge would make ordinary code integration an external package release.

The source repository, Git tag, GitHub Release, Release asset, npm version, and npm dist-tag are separate surfaces. Automation must preserve those distinctions and must not turn a passing pull request into publication authority.

## Decision

Use npm Trusted Publishing with GitHub Actions. A single workflow subscribes only to the GitHub `release` event with activity type `published` and runs on a GitHub-hosted runner. It receives `contents: read` and `id-token: write`, stores no npm write token, and uses an exact trusted workflow filename.

Before publication, the workflow checks out the Release tag, runs complete verification, creates a fresh package archive, validates tag and channel metadata, downloads the same-named archive attached to the Release, and requires byte identity. It publishes the matched Release asset only after every check succeeds.

### Packaging preflight amendment (2026-09-16)

Alpha.33 exposed a compressor mismatch despite identical Node/npm version strings:
Homebrew and official Node builds produced different gzip bytes from an identical
tar stream. Pin release packaging to the qualified official Node distribution and
check exact Node, npm and zlib versions through the shared release pack helper.
Record the observed fingerprint with each archive. It establishes compatibility;
it is not runtime-distribution authentication. Ordinary consumer runtime support
and ordinary CI do not inherit these stricter release-only pins.

Move qualified packing, Release metadata validation, asset download and exact-byte
comparison before complete verification. An incompatible environment or asset then
fails before the long suite starts. After complete verification, pack again with
the same helper and recheck the retained Release asset before publishing it. This
detects a changed source or asset during verification and retains every original
publication condition. Do not replace byte identity with decompressed equality.

Semantic prerelease versions require a GitHub prerelease and publish under npm `next`. Stable versions require a non-prerelease GitHub Release and publish under npm `latest`. The package-level default remains `next`; the validated workflow supplies the selected dist-tag explicitly.

Publishing a draft, editing a Release, pushing a tag, merging a pull request, or manually dispatching a workflow cannot invoke this path.

## Consequences

- The maintainer's deliberate GitHub Release publication remains the human release action.
- Routine npm browser login, second-factor prompts, and long-lived npm write tokens leave the normal release path.
- Public-package provenance is generated by npm when its Trusted Publishing requirements are met.
- A missing asset, mismatched tag, wrong prerelease flag, old npm CLI, failed verification, or different archive stops before publication.
- The next new version must provide the first end-to-end evidence that npm accepted the configured OIDC identity. Existing versions are not replayed.
- npm package versions remain immutable; post-publication recovery uses deprecation, a corrected successor, and intentional dist-tag repair rather than replacing bytes.

## Alternatives considered

- Publish on every merge to `main`. Rejected because merge authority and package-release authority are different.
- Publish on any version-tag push. Rejected because a tag alone does not carry the reviewed Release notes, prerelease classification, or attached package boundary.
- Retain interactive local publication. Kept only as an emergency path outside this automation; it does not solve repeated authentication friction.
- Store an npm automation token in GitHub. Rejected because a long-lived write credential is broader and harder to rotate than workflow-bound OIDC.
- Use staged publishing for every version. Deferred; it adds a second approval ceremony that the owner did not request for the current Alpha path.
