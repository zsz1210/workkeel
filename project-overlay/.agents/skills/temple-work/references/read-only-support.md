# Bounded read-only support

Read before delegating an informational helper under an existing parent task. This reference grants no delegation, model or spending authority. Use supported native delegation only when authorized; otherwise inspect locally.

## Eligibility

All conditions must hold:

- One bounded question supports the parent's already authorized scope.
- The helper inspects permitted existing sources and returns findings, source/revision references and uncertainties. It makes no project or canonical writes, external writes or lifecycle mutations.
- It has no independent delivery or formal verification responsibility, no declared scarce shared resources and no need for independently recoverable ownership.
- The parent can maintain the read-only boundary. Use native read-only restrictions where supported; if that boundary cannot be maintained, do not dispatch.

Locating API callers or explaining an existing contract qualifies. Formal acceptance testing, Independent QA, implementation, starting a shared simulator, dependency installation and editing evidence do not. Tests can write files or acquire resources: classify effects, not command names.

## Dispatch and return

Provide the question, permitted sources, read-only boundary and return format. Native entrypoint/bootstrap instructions and relevant data policy remain required; a compact packet cannot override them. The runtime executes and waits. Do not create a child Work Item, reserve a governed worker or register an app task solely for informational support.

The helper stops after returning findings, source/revision references and unresolved questions. The parent checks currency and integrates the result. A helper response is not acceptance, Independent QA, a lifecycle handoff or release evidence. Recording findings requires the parent's existing write authority.

## Escalation

On requested writes, expanded scope, formal gate responsibility, shared resources or uncertain permission, stop and return the issue to the parent. Obtain required authority before expanded work and use existing Work Item/claim and governed parallel dispatch procedures. Never relabel an already reserved or attached worker as support to bypass cleanup, locks, resource accounting or handoff.
